# Contract verification — original FastAPI vs Django port

**Question:** does the Django backend produce *exactly* the same output as the
original `backend/app/main.py` FastAPI service from the MLOPS-NLP project?

**Method:** both services were run **side-by-side** with the **same model
artifacts** (`deepfake_fusion.onnx`, `AdaptiveFusion_best_model.pth`,
`model_config.json`), then the same requests were sent to each and the
responses compared field-by-field. Timing fields (`latency`, `uptime_s`) are
excluded — they are inherently non-deterministic; everything else, including
the **Grad-CAM PNG bytes**, is compared exactly.

**Result: 29/29 checks passed — the outputs are identical.**

| # | Check | Outcome |
|---|-------|---------|
| 1 | `GET /health` payload (excl. uptime) | identical |
| 2 | `GET /health` field set | same keys |
| 3 | `GET /model/metadata` full payload | identical |
| 4–14 | `POST /predict` on all 10 sample faces + `models/sample.jpg` (label, `prob_real`, `prob_fake`, `confidence`, `logit`, `threshold`, `fusion_weights`, `model_version`, `image_size`) | identical |
| 15–18 | `POST /predict/visualize?format=json` (`label`, `prob_fake`, `prob_real`, `target`, `alpha`) for fake/real targets | identical |
| 19–22 | Grad-CAM PNG (`image_base64`) for fake/real targets | **byte-identical** |
| 23 | Invalid upload (text file) — status code | 400 = 400 |
| 24 | Invalid upload — error body | identical |
| 25 | Error body shape `{error, detail, status_code}` | present |
| 26–29 | Missing `file` field (proper multipart & empty post) — status + **raw body bytes** (FastAPI's automatic 422 validation body) | identical |

Notes:

- The port ships the project's own **CI dummy weights** (the trained
  checkpoint was never in the provided archive). With those weights the
  verdict follows image statistics (brightness) rather than deepfake
  artefacts — the *pipeline and contract* are the original ones, and swapping
  in the real `AdaptiveFusion_best_model.pth` + `deepfake_fusion.onnx` in
  `backend/models/` switches every prediction to the trained model with no
  code change.
- Machine-readable results: `backend/reports/contract_verification.json`
  (generated by `scripts/verify_contract.py` of the build environment).
- UI verification (headless browser): homepage live demo (real `POST
  /predict`), sign-in/sign-up, dashboard KPIs, workbench upload + samples +
  webcam capture, verdict panel with fusion weights and latency chips,
  Grad-CAM overlay with fake/real class toggle, history with thumbnails,
  admin overview / model monitoring (live metadata) / users / audit /
  settings — all rendering with zero page errors.

## Archive audit — where the model files actually are

The uploaded `MLOPS-NLP_Project.rar` (16.5 MB, 185 entries) was searched
exhaustively — working tree, git history (all blobs), git-LFS, DVC pointers
and the raw rar listing. It contains **no model weights**, and the repo's own
configuration explains why:

| Evidence | Detail |
|----------|--------|
| `.gitignore` | `models/*`, `*.pth`, `*.onnx` — "versioned with DVC, never with Git" |
| `dvc.yaml` | the checkpoint is a *pipeline output*; "DVC caches it automatically and `dvc pull` restores it" — no DVC cache was archived |
| notebook logs | `Weights found: /content/model_output/AdaptiveFusion_best_model.pth (125.1 MB)` and `weights_source="kaggle_kernel"` — the weights are **downloaded from Kaggle at runtime** |
| arithmetic | the checkpoint alone is 125.1 MB; the whole rar is 16.5 MB — it cannot physically be inside |

What the archive *does* contain, and what this package integrates:

- the model **code** (`src/` — shipped verbatim) and the FastAPI service whose
  contract is reproduced 29/29 identically;
- the training **notebook outputs** (recovered from git history, commit
  `afa1240`, 2026-11-18): the real evaluation metrics (now in
  `backend/reports/metrics.json` and served by `/model/metadata`) and 5
  evaluation figures (now in `backend/media/figures/` and shown in the admin
  console): architecture diagram, test evaluation panel, fusion weights by
  class, Grad-CAM on test images, qualitative results.

The serving weights therefore remain the repo's CI dummy artifacts until the
125.1 MB trained checkpoint is dropped into `backend/models/` — after which
every prediction, probability and Grad-CAM comes from the trained model with
no code change.
